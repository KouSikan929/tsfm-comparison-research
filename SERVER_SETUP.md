# Server setup & sync guide

This documents how to get this project running on `sdxsrv02` (or any future
server), and why the process looks the way it does. Written after we hit a
real access snag on 2026-08-24 -- read section 1 before trying direct SSH
file transfer again.

## 1. Why Claude can't SSH in directly (and probably won't be able to)

`sdxsrv02.aidi.hiroshima-u.ac.jp:32816` is reachable and SSH key auth
*works* -- but your interactive login (via VS Code Remote-SSH + password)
lands you inside a **Docker container** (prompt shows something like
`kousikan@0fd986edb15a` -- that hex string is a Docker container ID, not a
real hostname), not on the bare host. The container's `~/.ssh/authorized_keys`
is a completely separate file from whatever `sshd` on the actual host (or
whatever process answers on port 32816) checks. Editing the container's copy
does not grant key-based access to the thing Claude's `ssh` client connects to.

**Practical consequence:** unless you (or a lab admin) can get a public key
into the *host-level* `authorized_keys` for your account -- which likely
needs admin help you said isn't available -- Claude cannot get a working,
non-interactive SSH session to run commands on this server directly. Don't
spend more time on this path unless something changes (e.g. an admin adds
the key, or you find a way to reach a bare host shell through VS Code before
it auto-attaches to the container).

**The workaround: GitHub as the sync layer.** You already have working
*interactive* access (VS Code, password). GitHub lets you push from wherever
you're doing the actual work and pull from inside your container yourself --
no host-level SSH needed for Claude at all. Claude preps commits locally;
you push and pull. See section 2.

## 2. GitHub sync workflow

### One-time setup

**A. Create the GitHub repo** (github.com -> New repository). Recommend
**private**, since this is unpublished thesis work. Don't initialize with a
README/license/gitignore -- this project already has all three-equivalent
content locally. Name suggestion: `tsfm-comparison-research`.

**B. Push the local repo** (already initialized as of 2026-08-24, first
commit already made). From a normal terminal on whichever machine you're
working from (this needs to go through *your* git credential flow, not
Claude's -- Claude will never run this step for you):

```bash
cd /path/to/tsfmds
git remote add origin https://github.com/<your-username>/tsfm-comparison-research.git
git branch -M main
git push -u origin main
```

If this is the first time pushing from this machine, Windows Git Credential
Manager (or your OS equivalent) will pop up a browser to authenticate --
that's expected, let it complete.

**C. Set up git auth on the server** (inside your container, one-time). SSH
deploy key is recommended over a personal access token -- repo-scoped, no
expiry surprises:

```bash
# inside your sdxsrv02 container shell
ssh-keygen -t ed25519 -C "sdxsrv02-container" -f ~/.ssh/github_deploy_key -N ""
cat ~/.ssh/github_deploy_key.pub
```

Copy that public key to: GitHub repo -> Settings -> Deploy keys -> Add deploy
key. Check "Allow write access" only if you'll ever push *from* the server
(usually you won't -- Claude/you push from the dev machine, server only
pulls). Then, still in the container:

```bash
cat >> ~/.ssh/config <<'EOF'
Host github.com
    IdentityFile ~/.ssh/github_deploy_key
EOF
chmod 600 ~/.ssh/config

git clone git@github.com:<your-username>/tsfm-comparison-research.git ~/tsfmds
```

### Ongoing workflow (every time code/data changes)

On the dev machine (with Claude, or by hand):
```bash
git add -A && git commit -m "..." && git push
```

On the server (inside your container, by hand -- Claude cannot do this part
for you until/unless the SSH access situation in section 1 changes):
```bash
cd ~/tsfmds && git pull
```

That's the whole sync loop. No file transfer tooling needed.

## 3. What's NOT synced via git (and why)

See `.gitignore`. Excluded because they're large and regenerate automatically:
- `data/checkpoints/` -- Lag-Llama's checkpoint; re-downloaded via `huggingface_hub` on first run
- `models/iTransformer/checkpoints/` -- per-market trained weights; regenerated by rerunning `run.py`
- `models/iTransformer/results/` -- iTransformer's own raw `pred.npy`/`true.npy` dumps; regenerated by rerunning training. (The actual deliverable results -- `data/results/<market>/*.csv` and the plots -- ARE synced.)
- Kronos/TimesFM's own pretrained checkpoints aren't in the repo at all -- they're cached under `~/.cache/huggingface` on whichever machine runs them, outside the project directory, and download automatically on first use.

## 4. Recreating the environment on the server

Same 4 conda envs as the Windows setup, Python 3.10 each -- commands below
are the Linux equivalents (no `condabin.bat`/`.exe` path juggling needed,
just `conda activate <name>` after the usual `conda init`).

```bash
conda create -n kronos python=3.10 -y
conda create -n lag-llama python=3.10 -y
conda create -n timesfm python=3.10 -y
conda create -n itransformer python=3.10 -y
```

**Check the A40's CUDA driver version first** (`nvidia-smi`) to pick the
right torch index URL -- cu124 worked for kronos/lag-llama/timesfm on the
Windows RTX 4060; iTransformer specifically needs `torch==2.0.0` per its own
`requirements.txt` (cu118 index worked on Windows, but on a modern A40 driver
a newer index may work too -- try cu118 first for reproducibility, fall back
to a compatible newer one if needed):

```bash
conda activate kronos
pip install torch --index-url https://download.pytorch.org/whl/cu124
pip install -r models/Kronos/requirements.txt

conda activate lag-llama
pip install torch --index-url https://download.pytorch.org/whl/cu124
pip install "setuptools<81"   # newer setuptools drops pkg_resources, which pytorch_lightning still needs
pip install -r models/lag-llama/requirements.txt

conda activate timesfm
pip install torch --index-url https://download.pytorch.org/whl/cu124
pip install -e "models/timesfm/src[torch]"   # note: src/, NOT the legacy v1/ package
pip install pandas matplotlib   # not in timesfm's own requirements, needed by our eval scripts

conda activate itransformer
pip install torch==2.0.0 --index-url https://download.pytorch.org/whl/cu118
pip install -r models/iTransformer/requirements.txt
```

**Known gotchas already hit once on Windows, may or may not recur on Linux:**
- `lag-llama`'s checkpoint needs `torch.load(..., weights_only=False)` --
  already patched into `scripts/eval_lagllama.py` and the smoke-test script,
  no action needed, just don't remove that patch.
- Running 3 `iTransformer` trainings in parallel crashed on Windows
  (`WinError 1455`, paging-file exhaustion from `num_workers=10` x 3). This
  was a **Windows-specific** multiprocessing issue -- Linux doesn't have the
  same small-per-process-pagefile behavior, so parallel training is probably
  fine on the A40 server, but if something crashes similarly, retry
  sequentially or pass `--num_workers 0`.
- yfinance data can contain corrupted rows (see CSI300 incident, 2026-08-24
  -- one NaN close price + absurd volume spike on the most recent date).
  `scripts/download_data.py` doesn't currently check for this automatically
  -- worth spot-checking new downloads (`df.isna().sum()`, check for
  volume/price outliers) before trusting them, especially the most recent
  rows.

## 5. Running the pipeline

Same scripts, same commands as documented in `data/results/`'s per-market
outputs and the two notebooks in `notebooks/` -- just run from the
appropriate conda env, e.g.:

```bash
conda activate kronos
python scripts/eval_kronos.py --dataset SP500
```

See `notebooks/02_progress_and_next_steps.ipynb` for the full pipeline
narrative (windowing -> per-model eval -> aggregate -> plot) and
`scripts/eval_itransformer.py`'s docstring for the iTransformer-specific
train-then-eval two-step.
